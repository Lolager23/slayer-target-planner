# Automatic Windows updates — 4.0.0

Version 4.0.0, prepared on 22 November 2026, is a major update from 3.0.27. It includes saved calculations, Eclipse burn, travel options, the organised distribution layout and the Maxed-only default character. See the root verification record for release evidence.

## Behaviour

An unreleased [restart handoff correction](updater-restart-handoff.md) fixes the
Windows PowerShell process-lifetime failure reported after 4.1.1 publication.
Its evidence includes the real launcher-parent exit boundary; the original
release checks below did not cover that boundary.

The packaged Windows x64 app checks `https://api.github.com/repos/Lolager23/slayer-target-planner/releases/latest` at startup without delaying the window. It uses the public endpoint without a token, account name or character information. Development builds and the browser site do not run the native updater. Only a strictly newer stable three-part version is eligible; drafts, prereleases, equal versions and downgrades are ignored.

Automatic updates default on. A newer verified ZIP downloads in the background with a percentage banner. Once ready, closing the app normally installs it; **Restart and update** closes, installs and reopens it. The application waits for its main process and remaining processes from that installation to exit rather than killing them. The helper runs from its job directory, so its own working directory does not lock the app folder.

Settings shows the installed version, the newest version found, update status, **Check for updates**, **Restart and update** when ready and the automatic-update checkbox. Turning automatic updates off stops a current network check/download and prevents installation on close. Manual checking/downloading and an explicit restart remain available while off. These choices belong to this installation, not to a character. Network, rate-limit or verification failures leave the planner usable and offer the fixed GitHub releases link.

Existing 3.x executables contain no startup updater. They need a one-time manual download of the first published 4.0.0 Windows build. Future releases must use the updated packaging/share tools and the existing Windows asset naming convention.

## Verification and installation

The feed accepts exactly one version-matching Windows archive from this repository, with an explicit GitHub SHA-256 digest and a maximum compressed size of 512 MiB. Downloads stream to an app-owned partial file, with timeouts, bounded redirects, exact byte counts and digest verification. Redirects stay on the fixed GitHub API/repository and GitHub release-asset hosts. No release body or remote script is executed. An interrupted partial download is replaced on retry.

At installation, bundled Windows PowerShell code reads a data-only job, rechecks the ZIP digest/size, rejects traversal, duplicate names, Windows special names and symlinks/reparse entries, and limits archive count and expansion. The extracted `resources/update-manifest.json` must match the expected version, Windows/x64 and this repository. Every application file must appear in `resources/SHA256SUMS.txt` and match its hash. These metadata files are generated by the package/share tools. No Node installation or administrator prompt is needed; the app folder must be writable.

The helper stages a complete new folder beside the installation, renames the original to a unique backup and moves the new folder into the original path. The installation path therefore stays stable across updates, even if its original folder name contains an older version. A copy of the verified latest ZIP and its checksum stays inside its `share/` folder for sharing. The backup preserves user-added files as well as the original app. It moves into the app's update storage when the volume permits; otherwise it stays beside the installation. It is never silently deleted. Successful updates remove their extra downloaded ZIP cache. Backups consume space and may be removed manually after confirming an upgrade.

Character files, browser local storage and IndexedDB calculations remain in the unchanged Electron user-data directory outside the app folder. The product name/application ID and character backup schema stay unchanged. Updater settings and pending jobs live under `userData/updates`. Renderer IPC accepts a fixed action set only from the packaged main document; the renderer cannot supply an executable, download URL or installation path.

An interrupted folder swap or a failed relaunch restores the previous folder when the new installation is not running. Restarted apps acknowledge their version after displaying their window. If the new process remains alive without confirming startup, the helper keeps both copies instead of killing a possibly active app. A failed update pauses automatic retries; Settings can retry explicitly. This is not a guarantee of recovery from power loss, filesystem damage or every application-level regression. Restore a retained previous copy manually if needed.

## Focused verification

- Release/version selection, fixed origins, missing/duplicate assets, absent digests, size bounds, redirects, corruption, offline/rate-limit responses and partial-file cleanup.
- Startup concurrency, staged-result restoration, persistent opt-out, manual checks while disabled, install-on-exit queuing, trusted renderer IPC and preload event isolation.
- Actual Windows PowerShell extraction/hash/folder replacement using disposable fixtures, retaining extra files and separate synthetic character storage. Malicious ZIP cases fail for their specific expected reasons.
- Actual folder rollback after an injected interruption between renames. Failed and acknowledged restarts use a mocked process-launch boundary; the user's running application is not closed or launched for these tests.
- All 26 focused checks passed, along with TypeScript and the production build. A disposable packaged 4.0.0 app was inspected for native updater/helper source parity, UI assets and version/manifest parity; the updater-only increment left the calculation fingerprint unchanged. The release also corrects combat-cache identity, so that calculation change receives a new fingerprint. The anonymous live GitHub feed check passed without downloading an older release. A synthetic browser preview verified progress, ready/restart and opt-out feedback. The requested 4.0.0 release also runs the full suite; see the current verification record. A live production upgrade to a future GitHub release remains untested until such a release exists.

Primary references: [Electron's supported native Windows updater formats](https://www.electronjs.org/docs/latest/api/auto-updater), [GitHub releases API and asset digests](https://docs.github.com/en/rest/releases/releases). The existing app is a portable ZIP rather than an MSIX/Squirrel installation, so its updater handles that distribution format directly.
